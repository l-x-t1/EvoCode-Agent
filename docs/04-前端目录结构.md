# 04 — 前端项目目录结构

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v0.1（设计阶段草案） |
| 工程形态 | 仓库三目录：`frontend/`（本文档重点）· `backend/`（doc 06/07 定义）· `docs/` |
| 构建工具 | Vite 5 + TypeScript（strict） |
| 状态管理 | Zustand（按 feature 切片） |
| Mock | MSW（Mock Service Worker），`VITE_API_MODE=mock|live` 切换 |

## 1. 设计原则

1. **feature-first**：业务代码按功能域组织，页面级复用组件上升为跨域组件；新增一个页面 = 新增一个 feature 目录，不改动其他模块。
2. **类型即契约**：所有 API 类型集中在 `types/api.ts`（与后端 schema 对齐），Mock fixture 与真实响应共用同一类型，防止「Mock 一套、真实一套」。
3. **UI 与数据分离**：组件不直接 fetch，一律走 `features/*/{api,store}` 分层，便于 Mock/真实无缝切换。

## 4. 分层与数据流约定

```
组件 → features/*/store.ts (Zustand) → features/*/api.ts → api/client.ts → REST
                                        ↘ api/sse.ts → features/workspace/useRunStream.ts → store（事件入库）
UI 状态(选中/tab/抽屉) 存各 feature store；跨页共享仅 uiStore/connectionStore
```

- **Zustand 切片规范**：每个 feature 一个 `store.ts`（`create` + 可选 `devtools`）；命名 `useXxxStore`；禁止组件间直接互相 import 对方 store（通过路由参数或提升到公共层解决）。
- **请求函数命名**：`fetchTasks` / `createTask` / `reviewCandidate`，返回 `Promise<T>`，错误统一抛 `ApiError`（由 `client.ts` 归一化）。
- **SSE 事件处理**：`useRunStream` 只做「订阅 → 归一化 → 派发」，业务归并逻辑写在 feature store 的 reducer 中，保证 Workflow 页可复用同一事件流。

## 5. Mock 策略与标注（对应 PRD §6）

1. `VITE_API_MODE=mock` 时在 `main.tsx` 动态 `import('./mocks/browser')` 启动 MSW；`live` 时该分支被 tree-shake，Mock 代码不进生产包。
2. **SSE 模拟器** `eventPlayer.ts`：按「剧本」(fixture scenario) 定时派发事件序列（planner 计划 → 工具调用 → diff → 审批暂停 → 批准 → 测试 → 完成），用于完整演示审批流。
3. fixture 数据必须体现「故事性」：至少包含 1 个运行中任务、1 个等待审批任务、1 个失败任务、1 个待审候选 Skill、若干已完成任务，保证每个页面状态都能被展示。
4. 所有由 Mock 驱动的区块，其最近容器必须挂 `MockBadge`（右上角「模拟数据」角标），接入真实 API 后随开关消失——这一规则列入 UI 评审 checklist。

## 6. 命名与代码规范

| 项 | 规范 |
| --- | --- |
| 组件文件 | `PascalCase.tsx`，与组件同名；hooks `useXxx.ts` |
| 类型 | API 类型 `PascalCase`；枚举用 `union type`（如 `type TaskStatus = 'queued' \| ...`），不用 enum |
| 路径别名 | `@/` → `src/`；禁止 `../../` 跨三层以上引用 |
| 提交 | Conventional Commits（`feat: / fix: / docs: / chore:`） |
| 质量门 | ESLint + Prettier + `tsc --noEmit`；P0 起即启用，不后补 |
