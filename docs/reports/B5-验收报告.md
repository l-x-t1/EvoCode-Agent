## 一、核心红线：审核闸门（修订要求）

**未经测试与审核的候选 Skill 不得覆盖正式 Skill** —— 逐层落地并有测试证明：

1. 候选一经创建（服务生成或人工提交）固定 `pending`，`propose_candidate_from_run` 有断言「生成即 pending」；
2. 唯一发布路径 = `POST /skills/candidates/{id}/review`（decision=approved）→ 才创建正式版本、`current_version` 前移、evolutions+1；pending 存续期间正式版纹丝不动（test_candidate_review_gate 中段断言）；
3. rejected → 仅记录，不产生任何版本（test_candidate_rejected_publishes_nothing）；
4. 终态不可逆：重复审核 → 409 conflict（含 currentStatus details）；
5. create 类候选缺 skill_id 时拒绝发布（409）。

## 三、候选基于执行反馈生成（MVP 口径）

`SkillService.propose_candidate_from_run(run_id)`：从真实 run 反馈（任务标题/失败步骤/涉及工具/计划步骤）确定性抽取生成候选（内容 = 适用场景 + 执行要点 + 注意事项），**生成即 pending、不自动发布**；自动触发接线（run 失败时自动调用）待 GLM_API_KEY（当前为纯抽取式，LLM 增强列入 key 就绪后）。evidenceTaskIds 记录来源任务。
